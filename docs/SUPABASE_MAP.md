# Umwelt RP — карта Supabase (SUPABASE_MAP)

Что лежит в базе Supabase, кто и как к этому обращается, какие правила защищают данные.
Составлено **по самой базе** (запросы к системным каталогам Postgres, советник Supabase, пробные запросы под
ролями `anon`/`authenticated` в откатываемой транзакции), сверено с кодом. Проверено 2026-11-04, после версии 0.19.
Секретов и личных данных здесь нет: ни ключей, ни паролей, ни почт, ни идентификаторов пользователей.

**Обновлять в том же коммите**, где меняется структура базы: таблица, столбец, ограничение, индекс, политика RLS,
права, функция, триггер, бакет Storage, настройка Auth, на которую опирается код. Записывать только то, что
проверено в самой базе (правило в `CLAUDE.md`).

Связанные документы: правила и процессы — `docs/РУКОВОДСТВО.md` (раздел 6а «Аккаунты», 6г «Карта и редактор»),

## 3. Таблицы `public`

### 3.1. `characters` — персонаж аккаунта

Один аккаунт — один персонаж. Источник имени, постоянного ID и пола игрока.

| Столбец | Тип | Пусто? | По умолчанию | Назначение |
|---|---|---|---|---|
| `user_id` | `uuid` | нет | — | владелец, **первичный ключ** → `auth.users(id)` `ON DELETE CASCADE` |
| `name` | `text` | нет | — | имя персонажа «Имя_Фамилия» |
| `created_at` | `timestamptz` | нет | `now()` | когда создан |
| `id` | `bigint` | нет | `GENERATED ALWAYS AS IDENTITY` (последовательность `characters_id_seq`, с 1, шаг 1) | **постоянный ID игрока** (`Player.id` в игре, показывается в скобках: `John_Miller (5)`) |
| `gender` | `text` | нет | `'m'` | пол модели: `m` / `f` |

Ограничения и индексы:

| Имя | Что | Зачем |
|---|---|---|
| `characters_pkey` | `PRIMARY KEY (user_id)` | не больше одного персонажа на аккаунт |
| `characters_user_id_fkey` | `FOREIGN KEY (user_id) → auth.users(id) ON DELETE CASCADE` | удалили аккаунт — удалился персонаж |
| `characters_id_key` | `UNIQUE (id)` | ID не повторяется |
| `characters_name_lower` | уникальный индекс по `lower(name)` | нельзя занять имя, отличающееся только регистром |
| `characters_name_check` | `name ~ '^[A-Z][a-z]{1,14}_[A-Z][a-z]{1,19}$'` | формат РП-имени (как `Account.valid_name` в игре) |
| `characters_gender_check` | `gender IN ('m','f')` | только два значения |

`id` — `GENERATED ALWAYS`: игрок не может прислать свой номер, база выдаёт его сама. Номера идут с пропусками:
неудачная вставка (занятое имя, неверный формат) тоже тратит номер. Это нормально: ID должен быть уникальным,
а не сплошным.

RLS включён. Политики:

| Политика | Команда | Роль | Условие |
|---|---|---|---|
| «свой персонаж: создание» | `INSERT` | `authenticated` | `WITH CHECK (user_id = auth.uid())` — только для себя |
| «свой персонаж: чтение» | `SELECT` | `authenticated` | `USING (user_id = auth.uid())` — видно только своего |

Политик на `UPDATE` и `DELETE` нет: переименовать, сменить пол или удалить персонажа через API нельзя.
Проверено: обновление и удаление под ролью игрока затрагивают 0 строк. Если понадобится смена имени или
внешности — делать отдельной функцией с проверками, а не общей политикой `UPDATE`.

Кто использует:

| Где | Запрос | Игровая система |
|---|---|---|
| `scripts/account.gd` `load_character()` | `GET /rest/v1/characters?select=id,name&user_id=eq.<свой>` | вход: есть ли персонаж |
| `scripts/account.gd` `create_character()` | `POST /rest/v1/characters` (`user_id`, `name`, `gender`) | создание персонажа (ошибки `23505` — имя занято, `23514` — неверный формат) |
| `scripts/server_only/server.gd` `_verify()` | `GET /rest/v1/characters?select=id,name,gender&user_id=eq.<игрока>` **с токеном самого игрока** | вход на игровой сервер: имя, ID, пол → `GameState.join_player` |

Деньги, вещи, одежда, позиция в Supabase **не хранятся** — они в файле мира на игровом сервере
(`server_world.json`, ключ игрока `sb:<user_id>` в `GameState.uids`).

### 3.2. `admins` — кто может отправлять карты

| Столбец | Тип | Пусто? | Назначение |
|---|---|---|---|
| `user_id` | `uuid` | нет | **первичный ключ** → `auth.users(id)` `ON DELETE CASCADE` |
| `note` | `text` | да | пометка для людей (кто это) |

Записей: 1 (владелец проекта). RLS включён, **политик нет намеренно**: ни игроки, ни гости не могут ни читать,
ни менять таблицу. Проверено: под `anon` и под игроком видно 0 строк. Читает её только функция `is_admin()`
(раздел 5). Советник Supabase отмечает «RLS включён, политик нет» (уровень INFO) — это ожидаемо.

Добавить админа — только через SQL с правами владельца базы (панель Supabase или Claude через MCP).

### 3.3. `map_drafts` — черновики карты из редактора

| Столбец | Тип | Пусто? | По умолчанию | Назначение |
|---|---|---|---|---|
| `id` | `bigint` | нет | `nextval('map_drafts_id_seq')` | номер черновика, **первичный ключ** |
| `user_id` | `uuid` | нет | `auth.uid()` | кто отправил → `auth.users(id)` `ON DELETE CASCADE` |
| `created_at` | `timestamptz` | нет | `now()` | когда |
| `note` | `text` | нет | `''` | подпись (редактор пишет дату и число объектов) |
| `data` | `jsonb` | нет | — | карта в формате `GameWorld.map_data()`: `w`, `h`, `spawn`, `rows`, `props` |

Ограничения: `map_drafts_pkey`, `map_drafts_user_id_fkey`, `map_drafts_note_check` (`char_length(note) <= 200`),
`map_drafts_data_check` (`octet_length(data::text) <= 2 000 000` — не больше ~2 МБ).
Индекс только по `id`. Записей сейчас: 0.

RLS включён. Политики:

| Политика | Команда | Роль | Условие |
|---|---|---|---|
| «admin inserts own drafts» | `INSERT` | `authenticated` | `user_id = auth.uid()` **и** `is_admin()` |
| «admin reads own drafts» | `SELECT` | `authenticated` | `user_id = auth.uid()` **и** `is_admin()` |

Проверено: вставка под аккаунтом владельца проходит, под аккаунтом бота — ошибка `42501`
(«new row violates row-level security policy»); игрок видит 0 черновиков и удалить ничего не может.

Кто использует: `scripts/map_editor.gd` `_on_send()` → `POST /rest/v1/map_drafts`. Игра и игровой сервер таблицу
**не читают**. Читает Claude через Supabase MCP и выпускает черновик как `maps/city.json`
(руководство, раздел 6г). Карта в игре не зависит от этой таблицы.

### 3.4. `account_deletions` — журнал удалённых аккаунтов (с 2026-11-04, BF-044)

| Столбец | Тип | Пусто? | По умолчанию | Назначение |
|---|---|---|---|---|
| `id_hash` | `text` | нет | — | **первичный ключ**: `sha256` от id пользователя (hex, нижний регистр) — сам id не хранится |
| `deleted_at` | `timestamptz` | нет | `now()` | когда удалён |

Записи пишет только триггер `on_auth_user_deleted` (раздел 6); записи старше 90 дней он же удаляет при каждом
удалении. RLS включён, **политик нет намеренно**; прав у `anon`/`authenticated` нет (`42501` при чтении —
проверено). Читают через функцию `deleted_accounts()` (раздел 5). Записей сейчас: 0.
Комментарий таблицы: «sha256(id) удалённых аккаунтов для игрового сервера; 90 дней».

Зачем: игровой сервер хранит персонажа в своём файле под ключом `sb:<user_id>` и сам не узнаёт, что аккаунт
удалён. Раз в 5 минут он спрашивает отпечатки и убирает совпавших персонажей (`server.gd` `_sync_deleted`,
`drop_deleted`).

## 4. Связи

```
auth.users (Supabase)
   ├──< characters.user_id   (1 : 0..1, ON DELETE CASCADE)   имя, постоянный ID, пол
   ├──< admins.user_id       (1 : 0..1, ON DELETE CASCADE)   право отправлять карты
   └──< map_drafts.user_id   (1 : много, ON DELETE CASCADE)  черновики карты

is_admin()  ──читает──>  admins
map_drafts (политики)  ──вызывают──>  is_admin()
delete_my_account()  ──удаляет──>  auth.users (свою строку) ──каскад──> characters, admins, map_drafts
auth.users (удаление) ──триггер on_auth_user_deleted──> record_account_deletion() ──пишет──> account_deletions
deleted_accounts()  ──читает──>  account_deletions   ← игровой сервер (anon)
```

Между нашими таблицами прямых внешних ключей нет — всё связано через `auth.users`.
В игре связь одна: `characters.id` = `GameState.Player.id` (правило 10 руководства: всё, что принадлежит игроку,
привязано к этому ID).

## 5. Функции

| Функция | Возвращает | Язык | Права выполнения | Свойства |
|---|---|---|---|---|
| `public.is_admin()` | `boolean` | SQL | `authenticated` (у `anon` и `PUBLIC` отозвано) | `STABLE`, `SECURITY DEFINER`, `search_path = public` |
| `public.delete_my_account()` | `void` | plpgsql | `authenticated` (у `anon`, `PUBLIC` отозвано) | `SECURITY DEFINER`, `search_path = ''` |
| `public.deleted_accounts()` | `table (h text)` | SQL | `anon`, `authenticated` (у `PUBLIC` отозвано) | `STABLE`, `SECURITY DEFINER`, `search_path = ''` |
| `public.record_account_deletion()` | `trigger` | plpgsql | только владелец и `service_role` | `SECURITY DEFINER`, `search_path = ''` |

Тело: `select exists (select 1 from public.admins where user_id = auth.uid())`.

- `SECURITY DEFINER` нужен, чтобы функция могла прочитать закрытую таблицу `admins`. Узнать она позволяет
  только одно: «админ ли **я**». Других пользователей проверить нельзя (аргументов нет).
- Вызывают: политики `map_drafts`; `account.gd` `check_admin()` → `POST /rest/v1/rpc/is_admin` при входе через
  «Играть» (ответ запоминается в `user://editor.cfg` — по нему видна кнопка «Редактор карты»).
- Советник Supabase предупреждает (WARN), что функцию можно вызвать через API. Здесь это намеренно (см. выше).

`delete_my_account()` (с 2026-11-04, BF-044): `auth.uid()` пусто → ошибка `42501`; иначе
`delete from auth.users where id = auth.uid()` — удаляется только свой пользователь; `characters`, `admins`,
`map_drafts` уходят каскадом, сессии и токены — каскадом Supabase. Вызывает `account.gd` `delete_account()`
(`POST /rest/v1/rpc/delete_my_account` со свежим токеном) с экрана «Аккаунт» → «Удалить аккаунт» после слова УДАЛИТЬ.

`deleted_accounts()`: последние 5000 отпечатков из `account_deletions` (новые первыми). Вызывает игровой сервер
publishable-ключом (`server.gd` `_sync_deleted`, раз в 5 минут, первый раз через 2 с после запуска). Отдаёт
только отпечатки — по ним нельзя узнать id, не зная его заранее. Права у `authenticated` игре не нужны (оставлены
при создании; вреда нет — те же отпечатки).

`record_account_deletion()` — триггерная функция: `sha256(id)` в журнал (повтор — обновляет время), чистка старше
90 дней.

Проверено пробными запросами в откатываемой транзакции (2026-11-04, после создания): гость не может вызвать
`delete_my_account()` и прочитать `account_deletions` (`42501`); пользователь с персонажем вызывает
`delete_my_account()` — пользователя и персонажа больше нет; гость через `deleted_accounts()` получает отпечаток
`9af645a8…b6e76a`, совпадающий с тем, что считает игра (`String.sha256_text()`, тест в `audit_test.gd`).
Через HTTP (PostgREST) из рабочей среды Claude проверить нельзя (прокси не пускает) — это проверяет CI
`auth-test.yml`: сервер с аккаунтами пишет «журнал удалённых аккаунтов: доступен».

Других функций в `public` нет.

## 6. Триггеры

В `public` триггеров нет. На `auth.users` — один наш (с 2026-11-04, BF-044):

| Триггер | Таблица | Когда | Функция |
|---|---|---|---|
| `on_auth_user_deleted` | `auth.users` | `AFTER DELETE`, на каждую строку | `public.record_account_deletion()` |

Срабатывает при любом удалении пользователя: из игры (`delete_my_account`), из панели Supabase, админским API.
Персонаж при регистрации по-прежнему создаётся отдельным запросом игры, а не триггером.

## 7. Права ролей (GRANT) и RLS

Роли Supabase: `anon` — запрос без входа (только publishable-ключ), `authenticated` — вошедший игрок,
`service_role` — полный доступ (ключ нигде в проекте не используется).

| Таблица | RLS | `anon` (права на таблицу) | `authenticated` (права на таблицу) | Что реально разрешено политиками |
|---|---|---|---|---|
| `characters` | вкл. | **нет** | `SELECT`; `INSERT` только столбцов `user_id`, `name`, `gender` | вошедший: читать и создавать **своего**; гость: ничего |
| `admins` | вкл. | **нет** | **нет** | никому ничего (читает только `is_admin()`, `SECURITY DEFINER`) |
| `map_drafts` | вкл. | **нет** | `SELECT`; `INSERT` только столбцов `note`, `data` | админ: вставлять и читать **свои** |
| `account_deletions` | вкл. | **нет** | **нет** | никому ничего (читает только `deleted_accounts()`, пишет только триггер) |

С 2026-11-04 (миграция `tighten_role_grants`, закрытый аудит Н4, BF-041) у `anon`/`authenticated` только те права,
которыми пользуется игра (`account.gd`, `map_editor.gd`, `server.gd`); `UPDATE`, `DELETE`, `TRUNCATE`,
`REFERENCES`, `TRIGGER` отозваны. `id`, `created_at` (и `user_id` у черновиков) задаёт сама база — прислать их нельзя.
Последовательности не трогали (`map_drafts_id_seq`: `USAGE` у `authenticated` нужен для вставки).
Доступ к строкам по-прежнему решает RLS: RLS включён на **всех** наших таблицах, `FORCE RLS` выключен (владельца
базы политики не ограничивают — так и задумано).

Проверено пробными запросами от роли `authenticated` (в транзакции с откатом, после миграции): свой персонаж
читается; новый пользователь создаёт персонажа; `UPDATE`/`DELETE` своего персонажа, чтение `admins`, вставка
черновика со своим `user_id` — отказ прав (`42501`); `is_admin()` работает; админ вставляет и читает черновик;
гость не читает `characters` (`42501`).

**Права по умолчанию** (`ALTER DEFAULT PRIVILEGES`) для объектов, которые создаёт `postgres` в `public`: с
2026-11-04 новым таблицам — **ничего** для `anon`/`authenticated`, новым функциям — `EXECUTE` **никому**, кроме
владельца и `service_role` (у `PUBLIC`, `anon`, `authenticated` отозвано). Последовательности — как в Supabase
(`USAGE/SELECT/UPDATE`). Для объектов, создаваемых `supabase_admin` (панель Supabase), остались права Supabase
по умолчанию (всё — `anon`, `authenticated`).

**Важно для новых таблиц:** в той же миграции — `enable row level security`, политики **и** явные `grant` нужных
прав нужным ролям (без них игра получит `permission denied`); новым функциям для API — `grant execute`.

## 10. Auth (вход)

- Способ входа: почта + пароль (`/auth/v1/signup`, `/auth/v1/token?grant_type=password|refresh_token`).
  Токен живёт час, игра берёт свежий перед каждым входом (`account.gd` `refresh()`).
- Игровой сервер проверяет токен запросом `/auth/v1/user` и дальше читает персонажа **токеном игрока** —
  поэтому серверу не нужен сервисный ключ.
- Пользователей в `auth.users`: 2 (владелец и тестовый бот CI без прав).
- Пароли (с 2026-11-04, BF-045): защита от утёкших паролей **включена** — проверено по советнику Supabase (замечание
  `auth_leaked_password_protection` пропало); минимальная длина 8 и подтверждение почты — включены владельцем в
  панели (по его словам; через SQL эти настройки не читаются). Игра требует 8 символов при регистрации
  (`account.gd` `MIN_PASSWORD`) и понятно объясняет отказ (`explain`: `weak_password` → «утёк» / «минимум 8»).
  Капчи нет — решение владельца: Supabase требовал бы её и при входе, а показать её в игре нечем.
- Удаление аккаунта — `delete_my_account()` (раздел 5). Политика конфиденциальности:
  https://c0bectb11.github.io/Umwelt-RP/privacy.html (ветка `gh-pages`, `privacy.html`).
- Адрес после подтверждения почты (Site URL) — настройка панели, через SQL не читается. Нерешённый вопрос — BF-007
  (страница «Почта подтверждена» лежит в ветке `gh-pages`).
- Соединений Auth с базой: не больше 10 (советник Supabase, INFO) — для нынешней нагрузки достаточно.
